Radix Ordering Bench How many bits, how many passes, and which optimisations actually pay — measured against an exact comparison sort on a realistic label-priority key.

What this measures. Ordering is the first stage of label placement, and on large scenes it is a large share of the frame. This page isolates it: it builds a realistic priority-key distribution, runs each ordering variant on the identical data, and reports both cost (ms) and quality — where quality is measured two ways, because they disagree and only one of them matters.
  • Order agreement — fraction of positions identical to the exact sort. Strict, and pessimistic: reordering two labels of nearly equal priority counts as a miss even when it changes nothing on screen.
  • Decision agreement — fraction of labels whose placed / not placed outcome matches the exact sort, after running the same greedy placement over the same occupancy. This is the number that matters.
The three words this page keeps using, defined concretely.

Slots are counters — literally the length of the histogram array, new Int32Array(1 << digitBits). To sort by a digit that can take 2d values you need one counter per possible value, so a 12-bit digit means 4 096 slots. Two passes of 12 bits means 4 096 slots each, 8 192 total — that is why passes are cheap in memory and a single wide pass is not.

Precision is not about the float key; it is about how coarsely that key gets chopped up before counting. A counting pass cannot look at a float, so the observed key range is mapped onto integer levels: q = floor((key − lo) / (hi − lo) × (2bits − 1)). So bits decides how many levels the range is divided into, and any two labels landing in the same level become tied — the sort can no longer tell them apart and falls back to index order. Stability needs splitting in two, because conflating them is what makes this confusing. Sort stability — equal keys keeping their input order — is a property of the algorithm, and every variant here has it regardless of bit count. Temporal stability — labels not flickering between frames — is the one bits actually affect, and the mechanism is indirect: as the camera moves, lo and hi shift, so the level boundaries slide relative to the keys. Tied labels therefore swap order from frame to frame, and swapping two labels that compete for the same space changes which one wins. From 16 bits up the churn is identical to the exact sort — the quantisation adds no flicker of its own. Below that it adds real flicker, non-monotonically, because whether a given bit width happens to split a dense part of the key distribution is somewhat arbitrary.

So what should you actually use? 16 bits, one pass. That is bucket ordering with K = 65 536, and it is the first setting that is reliable rather than merely usually-fine:
  • Reliability, tested across 8 seeds × 3 sizes (24 scenes). 16 bits scored exactly 100% decision agreement and 100% weight kept in 24/24 cases. 14 bits failed 5/24, 12 bits failed 9/24, 10 bits failed 18/24. The failures are small (worst case 99.88% decisions, 99.44% weight) but they are real, and they are invisible if you test one scene — which is exactly the mistake an earlier version of this page made when it concluded "12 bits is enough" from a single lucky seed.
  • Zero extra flicker, per the churn table above.
  • Passes stop mattering at this precision. 16-bit 1-pass, 20-bit 2-pass and 24-bit 2-pass are within noise of one another at every size tested (the winner flips between them run to run). So take the single pass for simplicity — and if you already run a 20-bit 2×10 radix, there is nothing to fix.
  • Do not go to 24 bits chasing exactness. It buys order fidelity that placement never reads, and if you take it in one pass it costs 16.7 M slots and ~40× the time.
Against a comparison sort, any of these is 6–9× faster (0.070 vs 0.409 ms at 3k; 1.25 vs 11.1 ms at 60k). That replacement is the win; the bit width is a correctness setting, not a performance one.
What this page found, on a 24k-label scene at 3840×2160. Re-run it on your own numbers, but the pattern was consistent across sizes and viewports:
  • Precision saturates far below full float resolution — but 12 bits is not the floor, 16 is. On any single scene, 12 bits looks perfect; across 24 scenes it slips in 9 of them. 16 bits is exact in all 24 and adds no flicker. Everything above 16 bits buys order fidelity that placement never reads.
  • A single counting pass is enough at that precision. Bucket at 16 bits is within noise of 20-bit 2×10 radix at every size tested, and both are 6–9× a comparison sort. Replacing the comparison sort is the win; the choice among the linear methods is close to a coin flip on speed.
  • More passes lose here — but they are not useless in general. 24-bit 3×8 measured 0.607 ms, ~9% slower than 20-bit 2×10, because at these precisions the histogram already fits in cache and every extra pass is another full traversal. What passes actually buy is precision per byte of histogram: one pass at B bits needs 2B counters, p passes need p·2B/p. Hold precision fixed and vary only the pass count and the crossover is stark — at 24 bits a single pass costs 23.4 ms against 0.58 ms for two passes, a 40× gap, because it must clear and prefix-sum 16.7 M counters. Multi-pass loses on this workload only because label placement needs ~12 bits, where a single pass costs 16 KB of counters. See the Passes vs precision mode.
  • The three hand optimisations below mostly do not pay on this key distribution: fused histograms measured ~6% slower, key permutation ~3% slower, and skip-uniform-digit was within noise (it almost never fires, because real priority keys spread across the whole top digit). They are kept selectable so the result is reproducible rather than asserted.
  • Sorting the packed key natively is a dead end. Packing (key, index) into one double and calling comparator-free TypedArray.sort() — betting on the engine's fast path — measured 2.1 ms, roughly 4× slower than a bucket pass. It is still O(n log n); avoiding the JS comparator does not recover the gap.
  • Top-K is a real dial, not a free win. Truncating to the best K candidates cuts order + place from 0.82 ms to 0.52 ms (K=1000), but keeps only 80% of the placeable importance weight — 297 labels placed instead of 906. Quality rises monotonically with K (80% → 87% → 94% at K = 1k/2k/4k). Worth it only if you have a hard label budget anyway.
On naming. bucket, counting sort, and one-pass radix are three names for the same algorithm, which is why this page lists it once as “bucket / counting”. Scattering n items into K bins by a quantised key is a counting sort over K keys, and is an LSD radix with a single log₂(K)-bit digit. The only difference from the multi-pass radix rows is that it stops after one pass, so its key precision is log₂(K) bits rather than the full budget. The configurator's bucket ordering is exactly this, implemented flat.
Algorithms on this page, and what is deliberately left out.
  • Comparison sort — the exact reference. Every quality number is measured against it.
  • Bucket / counting — one pass, K bins. The practical winner here.
  • LSD radix — multi-pass, with the three candidate optimisations independently switchable.
  • Float-bit radix — radix on the double's high word: no min/max pass and immune to range outliers, but only ~20 mantissa bits of precision, so not lossless.
  • Packed native sort — one double per item, comparator-free native sort.
  • Top-K partial — bucket, then emit only the best K in bucket order.
  • Adaptive insertion — reuses the previous frame's order and repairs it. Only measurable in the Temporal mode, since a cold single frame is precisely the case where order reuse is worth nothing.
Left out on purpose: heap-based top-K (O(n log K) with per-item branching loses to a single counting pass at these K), quickselect-then-sort (two passes plus a partition, strictly more work than counting for a quantised key), samplesort / splitter-based schemes (they exist to parallelise; single-threaded they only add overhead), and importance-class-major bucketing — that one looks attractive because the key is importance-dominated, but with IMP_SCALE=5 the distance term spans ~16 log units while adjacent class offsets differ by ~6, so classes genuinely overlap in key space and a class-major pass would not be exact.
